Release assessment: follow-up required.
The most serious repaired issue allowed arbitrary chat IDs through ownership checks. Other fixes close legal-page editing and revoked-sharing access, prevent note loss and HTML injection, and preserve Scripture numbers. Unresolved dependency advisories, account-local data isolation and synchronization semantics remain material risks.

Scope and method

Inspected the Next.js frontend and its backend Route Handlers in frontend/src, auth/ownership helpers, persistence and sync flows, Prisma schema/migrations, Bible datasets, AI integrations, service worker and build configuration.

Inventory: 132 source files and 28 API route files. Used source review, cross-file data-flow tracing, TypeScript, ESLint, production builds, dependency audit, isolated behavior tests and a browser startup check. This is a broad source-based audit, not exhaustive execution of every user flow.

The top-level backend directory contains a Python virtual environment; the active application backend is implemented in Next.js. Historical HTML mockups, one-off fix scripts and the unrelated trading bot were excluded.

Boundaries and ownership

No deployment, database migration, production mutation, account deletion or paid AI request was performed. Existing secrets were not copied into this report.

Concurrent frontend changes appeared during the audit and were preserved. Their shell/dialog/accessibility work is described separately in FRONTEND-READINESS.md. F18 describes a shared worker fix; the final checks cover the combined tree.

“Fixed” means a change is present locally with the verification stated on that finding. “Needs review” means a product, data-migration, architecture, content or integration choice remains. “Blocked verification” is a coverage limit, not a newly proven production defect.

F01Chat ownership checks granted access to arbitrary IDsBackend · ChatCriticalFixed

Trigger / reproduction

A signed-in user requests another account’s numeric chat ID. ownsChat attempted to create that ID, then registered an owner-scoped memory chat when the database rejected the duplicate.

Impact / evidence

The message writer and history loader subsequently used chatId without an owner filter. This allowed cross-account message injection and exposure of prior messages to AI processing. An ordinary missing-ID read also created records.

Implemented fix

Ownership lookup is now read-only. An existing database record determines ownership; memory collisions cannot override it. Only previously registered memory chats are accepted. Message writes connect through the authenticated owner filter, and database history queries also filter the related chat owner.

Verification and limits

Behavior tests reject foreign, nonexistent, fractional and colliding IDs and verify no authorization-time writes.

F02Guest sessions were grouped by IP and had a public signing fallbackBackend · Guest identityHighFixed

Trigger / reproduction

Two browsers share an IP, or send no forwarded address. resolveChatIdentity always returned a guest owner key, so the cookie-creation branch in POST /api/chats never ran.

Impact / evidence

Unrelated guests could use the same server-side chat namespace. The literal signing fallback also made cookie signatures forgeable in an unconfigured environment.

Implemented fix

Unverified guests have no owner key. Chat creation issues a unique signed HttpOnly cookie. Signing requires GUEST_CHAT_SECRET or CLERK_SECRET_KEY. Malformed cookie encoding and invalid signature formats are rejected safely.

Verification and limits

Behavior tests create two guests on the same IP, verify separate cookies and denied cross-access, exercise malformed cookies, and check 503 when signing is unconfigured. Existing IP-based guest sessions are intentionally invalidated.
